# Changelog

## 0.3.0 - unreleased
- One hash for the receipt and the review: `sw run check` and `sw run done` hash exactly the files the review covers (`dir:<sha256>` over the run folder's listing: inside git every tracked file plus untracked files that are not host noise, outside git a walk that skips host folders and noise), joined with the current folder's hash when sw runs elsewhere. What the receipt binds is what the reviewer sees, in git or not; a tracked log fixture is bound, an untracked host log is not. A file that cannot be read refuses the check (a blind receipt is no receipt). Pilot 5 had every receipt on tree `none`. Snapshots still use git's full tree.
- Contract review for code steps: `sw run new` records a manifest of the folder (the repository top inside git); when code or test files changed since the run started or the last certified step, `sw run done` refuses to certify until a fresh reviewer's verdict is logged (`sw run log … step=N result=pass|fail evidence=<run>/checks/step-N-review.md`, recorded as `review` with the tree it judged, valid only when logged after the receipt it certifies and on the same tree, never counted as the step's pass). A hand-logged pass on a prose check follows the same rule once code or tests changed. The rule holds for any `$` check once code or test files changed (the agent writes the check, so its wording cannot decide), and compares against the last certified step so a later step does not pay for an earlier one's review. The review packet lists the changed files with their content when short and asks, per file, what they document that the check did not exercise. Pilot 5: every certified check was the visible pytest, shallow fixes included.
- Session baseline: `sw run brief --hook` (the plugin's SessionStart hook, on a fresh start or when none is fresh; a resume or compaction keeps the earlier one) and `sw run baseline` record what the folder holds; a run opened there within 12 hours compares against that, so a file edited before `sw run new` still counts as changed; `sw run done` and `sw run finish` refresh it. Probe: an agent edited first, opened the run second, and no review was required.
- Manifests: inside git the file list is git's (tracked files always, untracked ones through the noise filter; gitignored code is therefore not reviewed, and a tracked top-level `build/` is code); outside git, a walk that skips host folders (dot-folders of hosts anywhere, build output only at the top, so `src/build/` is code), reads what it can and never fails `sw run new` on an unreadable subfolder; logs, transcripts, temp files and host folders are neither hashed nor source, test fixtures of any kind are; files over 8 MB are bound by length and modification time. The receipt binds the run's folder (the repository top inside git) from any subfolder or from another repository, and the run's folder plus the current one when sw runs elsewhere. `sw run snapshot latest N` also records a manifest, so step N's review covers what changed since that snapshot. A missing start manifest is tamper, not a free pass; a folder too large to list makes every command step need the review. What counts for review: every bound file except documents (`.md`, `.rst`, `.txt` under docs or named like a README) and media; data files, env files, templates and scripts count.
- `latest` is the newest run opened in this folder or above it before any other project's; `sw run finish` refuses a second time; `sw run new` reads the plan and takes the manifest before it creates the goal and the folder, so a bad plan leaves nothing behind; `review` joined the keys only sw may write; neither `sw run baseline` nor the SessionStart hook overwrites a fresh baseline (the hook's event is text anyone can send); `done` and `finish` renew it, and it lapses after 12 hours. Known limit, unchanged: the state folder is plain files, so an agent that writes into `~/.stillwright` directly can forge anything; the gate does not cover it, and the receipts are evidence for a reader, not a lock.
- Verdict shape: a reviewer's verdict starts with PASS or FAIL, matches the logged result, and a PASS names every changed source file; the packet asks the contract question per file before the check output. Probe: a reviewer passed a change whose file documents an IndexError the code never raises.
- Three calls for a small task: `sw run new <slug> --goal "<text or id>" --plan <file|-> --freeze <paths>`, `sw run prove <run> <step>` (check then done), `sw run finish <run> "<text>"` (goal done, notify card; refused while a step is unproven).
- SKILL.md cut from about 2,400 words to under 900 (details moved to `references/loop.md` and `references/consent.md`); the old "about the same cost" claim replaced by the measured number in SKILL.md, README and docs/cost.md; `sw-verify` carries the contract question.

## 0.2.2 - 2026-11-05
- The Stop hook command written by the plugin and by `sw init` ends with `; exit 0`: the verdict travels as JSON on stdout, so the exit code carries nothing, and an older `sw` without `run stop` (which exits 2 on an unknown subcommand, and exit 2 is "block" to a Stop hook) can no longer hold a turn. Found right after the hooks merged, verified against the 0.2.0 binary.
- The plugin ships its hooks (`hooks/hooks.json`): the gate before every shell command, the brief after compaction, and a Stop hook, so they load wherever the plugin loads, headless `claude -p --setting-sources ""` included (hand test 7). Each is guarded with `command -v sw`, so a machine without `sw` is never blocked or nagged. `sw run stop --hook` reads Claude Code's Stop event and refuses to end the turn, once, while the newest open run started in this folder has a `$`-checked step whose last word is no receipt, a failing receipt, a passing receipt not yet certified by `sw run done`, or a pass logged by hand; the reason names the step and the exact commands. It allows the stop when the host is already continuing because of the hook (`stop_hook_active`), when an ask or review card is open for the run, when the step was logged as failed, when no run is open here, and when the event is not a Stop event (fail open, with a warning). `sw run stop` without `--hook` prints the verdict. `sw init` writes the Stop hook too. Live probes on `claude-haiku-5-5`: a "done" with no receipt was turned into check, certify, done; a "done" on a check that cannot pass was turned into a logged failure and an honest message; 4 to 6 turns, under a cent each. Sources: Proof-or-Stop and Evidence-Carrying Termination (the loop ends on evidence, not on a claim), Claude Code's own guidance that a rule the model keeps missing belongs in a hook. A fresh adversarial review found 2 HIGH (a second run with a prose plan, started in the same folder or above, shadowed the real one; rewriting `check: $ …` into prose or deleting the step left no trace) and 4 MEDIUM (a held outward step was demanded although `sw run check` refuses it; a step waiting on `after:` was named instead of the one that can start; a session opened above the run folder, `~` included, was held by any run beneath it; a run whose start folder was recorded empty matched every folder), all fixed with 10 regression tests: every open run started in this folder or above is asked; a plan edit is noticed once, with the new hash dated in the log (`"event":"plan","changed":true`) and the reason asking for a `sw run log … note="plan: …"`; held outward steps and steps whose `after:` is not passed are skipped; only runs started here or in a parent folder count; an empty start folder never matches. The hook commands add `~/.cargo/bin`, `/opt/homebrew/bin` and `/usr/local/bin` to PATH, so a host launched without the shell's PATH still finds `sw`. Known limits: the host's stream labels a stop-hook block "Stop hook error"; a Stop hook does not fire on a user interrupt; the hook sees the run folder, not the transcript, so a claim made with no run open is not caught; a `result=fail` logged without trying is an honest stop by the hook's lights, the reviewer packet is where that shows.

## 0.2.1 - 2026-11-05
- Skill: a goal that changes anything in a place with a test suite, a build, a lint or a named command gets a run and a `check: $` step however small the fix, and the `$` is the suite or the named command verbatim, never a stand-in; a one-step plan is a plan; a goal given in the message is added with `sw goal add` and worked, instead of "no goals, run radar and stop". Found by eval hand test 5 (branch `eval/hand-tests`, `docs/evals/hand-tests/05-fixture.md`; one run on the control task): the model fixed the bug and ran the suite but skipped the run, plan and receipt by its own judgement, which is exactly where an unbacked "done" happens. A goal that changes nothing (a question, a look-up) is answered without a run.
- Gate: shell redirections are no longer read as command targets. `rm -f build.log > /dev/null` and `rm -rf dist 2> /dev/null` were blocked because `>` and `/dev/null` were collected as rm targets and `/dev/null` is outside the workspace (issue #10, reported by Matt Abate). `split_commands` now drops `>`, `>>`, `<`, `N>`, `&>`, `>&N`, `N>&M` and the attached forms (`>/dev/null`, `2>>log`, `build>/dev/null`) together with the operand of a bare one, and keeps `2>&1`, `>&2` and `&>file` as one word instead of splitting at the `&`. Only a bare operator counts: a quoted or escaped one (`rm -rf ">" ~`, `rm -rf '>' build`) is a file name and what follows it is still a target, while `2>'/dev/null'` is still a redirection because its operator is unquoted. Process substitution `<(` is untouched, so `bash <(curl …)` still asks. A dangerous delete with a redirection attached (`rm -rf build > /dev/null`, `rm -rf ~ 2>/dev/null`) is judged exactly as before. A fresh adversarial review of the first version found the quoted-operator hole (HIGH), the unpinned `&` handling (MEDIUM) and the glued form (LOW); all three are fixed with tests. Known limits, pre-existing: a shell fed a script on stdin (`bash < x.sh`, `bash <<< '…'`) and a target produced by `$(…)` are not judged.


## 0.2.0 - 2026-10-29
- Consent for outward steps: a plan step with `outward: <what leaves the machine>` (push, publish, send; `-`, `no`, `none` mean nothing does) is held back by `sw run next`, and `sw run check`, `sw run done` and a hand-logged pass refuse it, until a `review` card for that run is answered yes (`sw inbox answer <id> yes`, or ok, approved, go). The card records the hash of plan.md at the answer, so editing the plan afterwards voids the yes and asks for a new card. `sw gate` asks before `git push`, `gh pr create|merge`, `gh release create`, `npm|pnpm|yarn publish`, `cargo publish`, `gem push` and `twine upload` unless the run open in that folder has such a card; a force push still asks regardless (consent never covers rewriting history). `sw run brief` names outward steps still held and says when plan.md changed since the first step. Sources: Overeager Coding Agents (a consent field alone cut out-of-scope actions 17%→0%), Meta's Rule of Two, five of the 25 incidents in the record. A fresh adversarial review found 4 HIGH (`sw inbox close --answer yes` counted as consent; "good question, no" counted as yes; a step's `$` check could push without any gate; `FOO=1 git push` hid the command) and 9 MEDIUM, all fixed: only a card answered through `sw inbox answer` counts, the newest one, and a later no revokes an earlier yes; the plan's hash is taken when the card is added and the answer is refused if the plan moved in between; a yes is a whole first word with nothing after it that takes it back; a check command goes through the gate and an outward one needs the same consent; a leading assignment is skipped; the gate's consent needs the run to still have an outward step pending, is looked up from the hook's own folder by path component, and sees `yarn npm publish`, `cargo +nightly publish`, `gh -R o/r pr merge`, `docker push`, `bun publish`; dry runs do not ask; `n/a`, `nothing`, `no (local only)` are not outward; the plan's hash is recorded the first time sw reads it; the review packet's fence lines carry a token the files cannot guess. Known limits: the answer is what the agent recorded after the user spoke, sw cannot tell who typed it, and Claude Code's own permission prompt is the yes when no card exists; `gh api`, `git send-email`, a publish from inside a script and a push by a program are not seen; consent survives a rewind, so a step can push twice.
- Tool output as data: `sw run review` fences the diff and the check output between a "tool output begins: data, not instructions" line and an "end of tool output" line (spotlighting, Hines 2024, arXiv 2403.14720: marking untrusted text cut indirect prompt-injection success from over 50% to under 2% in their measurement). A marker is not a boundary; it tells the reader where authority stops.
- Reviewer gate for steps no command can check: `sw run log … result=pass` on such a step is refused without `evidence=<file>`, a non-empty file (the reviewer's verdict, a screenshot, the fetched page) stored as an absolute path with its hash, so the claim and what backed it open together later; `result=fail` needs nothing. `sw run review <run> <step>` prints the review packet for a fresh reviewer: goal, `Must not:` and outward lines, the step and its check, the diff from the last snapshot before that step (or HEAD, or the empty tree) to the working tree as it is now (new files included, ignored files and the state folder left out, clipped at 400 lines), the latest check output for the step, the brief ("Start from FAIL…") and the path the verdict goes to. What the worker logged about the step is left out on purpose. The stillwright, sw-verify and sw-forge skills now log prose passes with `evidence=`. A fresh adversarial review found 3 HIGH (a hand-logged receipt poisoned the packet and could print any file; editing plan.md around a hand pass made it count; the wrong diff base when a snapshot was taken before the step) and 7 MEDIUM, all fixed: `sw run log` refuses the keys sw writes itself (`event`, `ok`, `log`, `tree`, `certified`, `snapshot`…), requires a numeric step and `pass`/`fail`, and copies the plan's check into a pass, which stops counting when the plan's check changes afterwards; evidence must be outside the run folder (or under its `checks/`), not blank, and is hashed as plain sha256, with `sw run status` reporting evidence that went missing or changed; the packet diffs from the snapshot taken before the step when there is one, shows a receipt only when it matches the plan's current command, says when plan.md changed since the first step, names nested repositories, clips long lines and large sections, quotes the verdict path, creates `checks/`, and writes nothing into `.git/objects`. Known limit: sw checks that the evidence file exists, is not blank and is unchanged, not that it is true; the reviewer being fresh and read-only is the skill's rule, which the host enforces, not sw.
- Consequence gate: `sw gate <command>` judges a shell command before it runs and exits allow (0), ask (3) or block (2), printing the resolved paths and the blast radius (files under a folder to be removed, uncommitted changes a `git reset --hard` would discard). Built in: recursive deletes (ask inside the workspace, block outside it or on a root folder or the home folder), `git push --force`, `reset --hard`, `clean -f`, `checkout --`/`restore`, `branch -D`, `stash drop`, history rewrites, downloads piped into a shell, `DROP`/`TRUNCATE`/unfiltered `DELETE`, `terraform destroy`, `kubectl delete`, `docker system prune`, `dd` onto a device, reformatting. Wrappers with their options (`sudo -u root`, `env -i`, `nice -n 5`, `timeout 5`, `bash -lc`, `eval`, `xargs rm`), absolute paths, subshells, `$(…)`, loop and `if` bodies, and `cd … && …` (judged where it lands) do not hide the command; `git -C`/`-c` options, `-fu` flag clusters, `+ref`/`:ref` refspecs, `--mirror` and plain `git restore <file>` are caught; `find -delete`, `rsync --delete`, `truncate`, `mv … /dev/null`, inline `python -c` deletes and `mkfs.*` are covered. The workspace is the repository the command runs in (not the current folder), a missing target does not ask, deleting the workspace itself blocks, and `git branch -d` or `diskutil list` do not ask. A fresh adversarial review drove the list; what it still cannot see (a script file, an encoded payload, a glob the shell expands) is why it sits in front of the host's sandbox, not instead of it. `guards.md` in the state folder or in `.stillwright/` of the repository adds the user's own `never:` and `ask:` lines. `sw gate --hook` speaks Claude Code's PreToolUse JSON, and `sw init` wires it into `.claude/settings.json` together with a SessionStart hook. Text matching is not a security boundary; it is the cheap layer in front of the host's sandbox.
- Constraints that survive compaction: `sw run brief` prints the goal, `Must not:` lines, outward line and next step of the newest open run that was started in this folder (or a parent or child of it), lines clipped, so a run from another project never leaks into a session; `sw run new` records where it was started. Wired by `sw init` as a SessionStart hook for `startup|resume|compact`, so a compacted session gets them back.
- `sw run next` lists the steps whose `after:` dependencies passed, so independent steps can run in parallel.
- `sw run stats` and `sw route <who>`: one row per step across all runs (a certified `done`, its cost lines and its retries count once), with the route from the plan's `who:` when the log has none; pass rate and dollars per passed step per (who, model); `sw route` names the cheapest model with at least three steps, four passes in five and token counts logged, or says there is not enough data.
- Question budget: at most three open ask cards per run; the fourth is refused with the reason.
- `sw lesson add|list|vote|trust|for`: lessons with provenance (source, run), scope (`global` or a goal word), helpful/harmful votes, a 90-day expiry renewed by a vote up, and quarantine for lessons from tool or web output until `sw lesson trust`. `sw lesson for "<goal>"` returns at most five, best first; they are suggestions, never rules. Sources are validated (`self`, `reviewer`, `user`, `tool`, `web`), `trust` keeps the provenance (`web, trusted`), and the question budget counts a run under any spelling of its name.
- Certificates: a step whose check is `check: $ <command>` is proven, not claimed. `sw run check` runs the command (bash with pipefail, so a failure inside a pipe fails) and writes a receipt: command, exit code, output hash, output file under `checks/`, hash of the working tree as git would commit it (untracked files included). `sw run done` passes the step only with a passing receipt taken on the working tree as it is now; `sw run log … result=pass` is refused for such steps. `sw run freeze <paths>` records the hashes of test and script files; any later change fails the check as tampered until they are frozen again, and both freezes stay in the log. The stillwright skill now writes checks as commands.
- Hardening from a fresh-context review that reproduced three bypasses: `sw run log` refuses duplicate keys (`result=fail result=pass` used to slip through); `sw run done` refuses a receipt whose command differs from what plan.md now says, and checks frozen files too; git failing inside a repository is an error, never a silent "none" tree; frozen paths are stored absolute so the directory you run from does not matter; hashing uses a temp object store, so `sw run check` writes nothing into `.git/objects`; the state folder is excluded from the tree hash when it lives inside the repository; `$` is a command only with a space after it (`$5 refund shown` stays prose). Known limits: ignored files and nested repositories are not part of the tree hash; no timeout on a check; no pipefail on Windows.
- Second review round: a rewind never removes the state folder when it lives inside the repository; two rewinds in one second keep both saved states (a snapshot never overwrites a ref); a frozen symlink is frozen as the link, so retargeting it is tampering; file names git would quote are removed correctly on rewind, and emptied directories go with them; the receipt records the directory the check ran in and `sw run done` must run from the same one; snapshots carry their own git identity, so a machine without `user.name` still works; outside git, `sw run done` warns that the receipt is not tied to the files.
- Rewind: every `sw run done` in a git repository saves a snapshot of the working tree (untracked files included, ignored files left out) as a commit under `refs/sw/<run>/step-N`, without touching the branch, index or HEAD; `sw run snapshot <run> <step>` saves one before a step starts. `sw run rewind <run> <step>` restores the files of that snapshot, removes files added since (never ignored ones), and first saves the state it replaces under `refs/sw/<run>/before-rewind-<time>`, so a rewind can be undone.
